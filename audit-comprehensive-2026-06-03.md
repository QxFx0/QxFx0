# Комплексный аудит системы QxFx0
Дата: 2026-06-03

## Резюме

Настоящий документ представляет собой комплексный аудит системы QxFx0 — детерминистической диалоговой среды выполнения с формальными основаниями. Аудит охватывает три ключевых аспекта: архитектуру системы, организацию модулей и паттерны внутренних связей. Выявлено 9 критических и высокоприоритетных уязвимостей, требующих немедленного устранения, а также 6 приоритизированных возможностей для улучшения архитектуры.

**Ключевые выводы:**
- Система демонстрирует зрелую 8-слойную архитектуру с механически проверяемыми инвариантами зависимостей
- Уникальный Self-слой реализует формальную модель самосохранения через функционал conatus
- Обнаружены критические проблемы неограниченного роста состояния и обработки исключений
- Предложена поэтапная дорожная карта улучшений с оценкой рисков

## 1. Что такое QxFx0

### 1.1 Назначение и область применения

QxFx0 — это исследовательская диалоговая система, которая приоритизирует воспроизводимость, трассируемость и формальную корректность над вероятностной правдоподобностью. В отличие от большинства современных разговорных систем, оптимизирующих беглость речи, QxFx0 оптимизирует:

- **Детерминированное поведение** — одинаковый вход + состояние → одинаковый выход, всегда
- **Трассируемые решения** — каждый выбор маршрутизации имеет проверяемые доказательства
- **Явные контракты** — режимы отказа типизированы, а не скрыты
- **Формальное обоснование** — грамматика GF + типизированная семантика, не шаблоны
- **Управление в приоритете** — история только для добавления, перестраиваемые проекции, версионированные политики

Система предназначена для сценариев, где вопрос "почему она так поступила?" должен иметь точный ответ: критическая инфраструктура, исследовательские инструменты, регулируемые среды.

### 1.2 Теоретические основы

QxFx0 основана на трёх взаимосвязанных тезисах:

**Тезис I — Сознание как структурированная двойственность**

Функциональная самость — это не отсутствие внутреннего противоречия, а **устойчивое структурированное сосуществование** несовместимых самопредставлений, удерживаемых без коллапса в одну из сторон. Это *двойственность* в формальном смысле (сопряжённая пара, антиподальная проекция), а не *конфликт* в обыденном смысле.

**Тезис II — Интенсивная спецификация**

Поведение должно специфицироваться **интенсивно** — через поля, потенциалы, тенденции, энергетические функционалы — а не **экстенсивно** через правила случай-за-случаем. Система описывает *к чему она стремится*; траектории возникают из релаксации в стремлениях.

**Тезис III — Conatus как первичный алгоритм**

Над всей внутренней структурой лежит единое первичное обязательство: система стремится **продолжать быть той системой, которой она является**. Это спинозовский *conatus* — внутреннее стремление вещи пребывать в своём бытии. Существует скалярный функционал `conatus(state) → ℝ`, и динамика каждого восстановления, каждого коммита предпочитает направления, не разрушающие этот функционал.

**Синтез:** Функциональная самость — это устойчивая структурированная двойственность системы, которая интенсивно стремится сохранить свою собственную структурную отличительность.

### 1.3 Ключевые характеристики

- **Язык реализации:** Haskell (GHC 9.6.6)
- **Лицензия:** MIT
- **Поддерживаемые языки:** Русский (основной), Английский (экспериментальный)
- **Статус:** Исследовательский уровень с готовым к продакшену ядром
- **Персистентность:** SQLite с контрактами схемы
- **Генерация текста:** GF (Grammatical Framework) + морфологический резолвер
- **Тестовое покрытие:** 45 тестовых наборов, 400+ примеров в золотом корпусе

## 2. Архитектура системы

### 2.1 Восьмислойная структура

QxFx0 организована в восемь горизонтальных слоёв. Зависимости текут **только вниз**, с одним исключением (`Runtime.GF.Morphology` доступен из верхних слоёв как чистая утилита). Правила между слоями механически проверяются скриптом `scripts/check_architecture.sh` (двенадцать пронумерованных инвариантов).

```
┌────────────────────────────────────────────────────────────────┐
│  App / CLI         (пользовательский интерфейс)                │
├────────────────────────────────────────────────────────────────┤
│  Runtime           (композиция, сессии, шлюзы, здоровье)       │
├────────────────────────────────────────────────────────────────┤
│  Core              (цикл сознания, конвейер диалога, защита)   │
├────────────────────────────────────────────────────────────────┤
│  Self              (SelfBlanket, Conatus, Adjunction, Field)   │ ← Уникально для QxFx0
├────────────────────────────────────────────────────────────────┤
│  Bridge            (SQLite, Datalog, свидетели Agda)           │
├────────────────────────────────────────────────────────────────┤
│  Semantic + Render (разбор, значение, генерация поверхности)   │
├────────────────────────────────────────────────────────────────┤
│  Lexicon + Policy  (словарь, парадигмы, политики оценки)       │
├────────────────────────────────────────────────────────────────┤
│  Types             (определения данных домена)                 │
└────────────────────────────────────────────────────────────────┘
```

**Ответственность слоёв:**

- **Types** — только определения данных; никакого IO, политик, решений. Сток графа зависимостей.
- **Lexicon + Policy** — словарь (парадигмы, поверхностные формы) и чистые политики (оценка, пороги). Без IO.
- **Semantic + Render** — вход → значение, значение → поверхность. Не должен импортировать Bridge/Core/Runtime.
- **Bridge** — границы персистентности и внешние: пул SQLite, тень Datalog, свидетели Agda.
- **Self** — типы и чистые функции, описывающие *что делает эту систему этой системой*. Импортируется Core, Bridge, Runtime.
- **Core** — цикл сознания, конвейер диалога (Prepare → Route → Render → Finalize), защита/восстановление, идентичность.
- **Runtime** — компонует Bridge + Core в работающую сессию; хостит шлюзы, здоровье, пути, проводку.
- **App / CLI** — точки входа (интерактивный CLI, HTTP-сайдкар).

### 2.2 Компоненты Self-слоя

Self-слой — уникальная особенность QxFx0, реализующая формальную модель самосохранения:

**SelfBlanket** (`QxFx0.Self.Blanket`)
- Конечный набор структурных инвариантов, одновременное сохранение которых определяет непрерывность бытия системы
- Нарушение любого инварианта — категорический отказ (`IdentityRupture`), не восстанавливаемая ошибка

**Conatus** (`QxFx0.Self.Conatus`)
- Скалярный функционал `RuntimeState → ℝ`, градиент которого задаёт первичное направление для восстановления
- Вычисляется один раз в `PrepareStatic` и разделяется по всему ходу (Фаза 6/M6.1)

**Holistic ⊣ Formal** (`QxFx0.Self.Adjunction`)
- Два сопряжённых функтора двухрежимной среды выполнения
- Формальная сопряжённость произведение-экспонента `(- × Field) ⊣ (Field → -)`
- Проверенные тождества треугольника как свойства QuickCheck

**Field** (`QxFx0.Self.Field`)
- Пятикомпонентная правополушарная сводка наблюдений:
  - `Resonance` — пиковое эхо текущего хода относительно недавнего контекста
  - `Atmosphere` — двумерный аффект валентность-возбуждение
  - `FieldConfidence` — производная оценка внутренней когерентности
  - `Consolidation` — скаляр нарративной интеграции в окне
  - `Counterfactual` — разнообразие правдоподобных альтернативных разборов

**Salience** (`QxFx0.Self.Salience`)
- Контроллер, решающий, какой режим ведёт за ход
- Основан на сигналах неоднозначности/новизны/формального отказа/временного давления

**Deliberation** (`QxFx0.Self.Deliberation`)
- Фреймворк согласования с расхождением тона (Фаза 8, Пакеты A/B/C/D)
- Функция `reconcile` заменяет переключение приоритетов в маршрутизации

**Essence** (`QxFx0.Self.Essence`)
- Отслеживание траектории с обнаружением разрыва (Фазы 9-10)
- Σ-тип `Essence` с морфизмами `witness`/`shouldCommit`/`extractMode`/`commit`
- Исключение `EssenceRupture` в политике исключений

**PerspectiveOperator** (`QxFx0.Self.Perspective`)
- Управляемое ядро мнений над знаниями, результатами диалога, позициями по утверждениям
- Канонический версионированный источник происхождения в `PerspectiveRegistry`

### 2.3 Конвейер обработки диалога

Один диалоговый ход проходит через четыре последовательные фазы:

```
вход ──▶ Prepare ──▶ Route ──▶ Render ──▶ Finalize ──▶ выход
           │           │         │           │
           │           │         │           ├─ Precommit  (разрешение канонического семейства ходов)
           │           │         │           ├─ Commit     (персистентность состояния + проекций)
           │           │         │           ├─ Dream      (офлайн-консолидация, перепрошивка рёбер)
           │           │         │           └─ State      (метрики после коммита)
           │           │         │
           │           │         ├─ Strategy / Anchor / Prefix / Cache
           │           │
           │           ├─ Phase  (парсер → подсказка графа значений → давление → вспышка интуиции)
           │           ├─ Cascade (защита, идентичность, порог)
           │           └─ Подсказка рендеринга
           │
           ├─ Resolve (семантический вход → SemanticInput)
           └─ Build   (сигналы хода: сознание, интуиция, нарратив)
```

**Детерминизм:** Конвейер детерминирован на уровне протокола — идентичный вход плюс идентичное персистентное состояние даёт идентичные решения. Недетерминизм ограничен временем, генерацией UUID и планированием процессов.

**Генерация текста (3 уровня):**
1. **GF (Grammatical Framework)** — формальная грамматика через PGF (приоритет)
2. **Haskell-линеаризация** — нативный фоллбэк с морфологическим резолвером
3. **JSON-словари** — предзагруженные парадигмы (родительный, винительный падежи и т.д.)

Никакого Python в пути выполнения. Никакой LLM для генерации. Чистый детерминизм.

### 2.4 Фазы разработки

Система прошла 10 основных фаз развития Self-слоя:

**Фазы 1-2** — Инварианты `SelfBlanket` и функционал `Conatus`

**Фаза 3** — Сопряжённость `Holistic ⊣ Formal` (ADR-0008)

**Фаза 4** — Правополушарная запись `Field` с пятью компонентами (ADR-0009)

**Фаза 5** — Контроллер значимости (ADR-0010)

**Фаза 6 / M6.1** — Рефакторинг Conatus с единым источником истины

**Фаза 7** — Инфраструктура структурной калибровки

**Фаза 8** (Пакеты A/B/C/D) — Фреймворк обсуждения (ADR-0011)

**Фазы 9-10** — Обязательство сущности с обнаружением разрыва

## 3. Организация модулей

### 3.1 Структура по подсистемам

Система содержит ~250 внутренних модулей, организованных в 10 основных подсистем под `src/QxFx0/`:

- **Bridge/** — SQLite, Datalog, свидетели Agda, персистентность
- **Core/** — цикл сознания, конвейер диалога, защита, идентичность
- **Self/** — SelfBlanket, Conatus, Adjunction, Field, Salience, Deliberation, Essence, Perspective
- **Semantic/** — разбор, атомы значения, сборка/декомпозиция
- **Render/** — генерация диалоговой поверхности
- **Lexicon/** — парадигмы, поверхностные формы
- **Policy/** — оценка, пороги, контракты
- **Runtime/** — сессии, шлюзы, здоровье, проводка
- **Types/** — чистые определения данных домена
- **Learning/** — дерево знаний, калибровка, развитие диалога

### 3.2 Граф зависимостей

**Types как сток графа:**
- Fan-in: 79 модулей импортируют Types
- Fan-out: 0 (Types не импортирует другие модули QxFx0)
- Роль: единственный источник истины для определений данных

**12 механически проверяемых инвариантов:**
1. Types не импортирует Core/Bridge/Semantic
2. Semantic не импортирует Bridge/Core/Runtime
3. Bridge не жёстко кодирует пути спецификаций
4. Bridge → Core запрещено; Core → Bridge/Runtime запрещено
5. Никакого `SomeException` в критических путях
6. Никакого частичного `read`
7. Никакого голого `head`/`tail`/`init`/`last`
8. Никакого голого `fail` в IO
9. Runtime импортирует шаблоны из Policy, не Lexicon
10. `EmbeddedSQL.hs` синхронизирован с `spec/sql/`
11. Открытые модули Core достижимы из Runtime
12. Доступ к `Holistic`/`Formal` только через `Self.Adjunction`

### 3.3 Критические точки интеграции

**Prepare → Route:**
- Вход: `SemanticInput`, `TurnInput` с Conatus/Field
- Выход: `CanonicalMoveFamily`, `IllocutionaryForce`

**Route → Render:**
- Вход: `CanonicalMoveFamily`, контекст диалога
- Выход: `RenderStrategy`, `DialogueAnchor`

**Render → Finalize:**
- Вход: сгенерированная поверхность
- Выход: `CommitPlan`, обновлённое `SystemState`

**Self ↔ Core:**
- `PrepareStatic` вычисляет Conatus/Field один раз
- `Route.Phase` потребляет энергию/поле
- `Deliberation.reconcile` вызывается при маршрутизации
- `Essence.commit` вызывается в Finalize

### 3.4 Ключевые структуры данных

**SystemState** (377 строк)
- Центральное состояние с 30+ полями
- Включает: интуицию, историю диалога, дерево знаний, защиту, временные атомы, снимки калибровки, историю управления

**TurnInput**
- Входные данные хода: семантический вход, энергия Conatus, поле, свидетель сущности

**TurnReplayTrace**
- Полная трассировка воспроизведения с полями восстановления, Conatus/Field, Essence

**CanonicalMoveFamily**
- Типизированные семейства ходов: Contact, Definition, Clarification, Acknowledgement, Challenge, Reflection, Synthesis, Boundary

## 4. Анализ внутренних связей

### 4.1 Сильные стороны

✅ **Механически проверяемые инварианты** — 12 правил зависимостей проверяются автоматически в CI

✅ **Чистое разделение слоёв** — Types как сток графа, Self изолирован, Semantic/Render отделены от Bridge/Core

✅ **Типизированные границы ошибок** — `ExceptionPolicy` определяет все категории исключений, никакого `SomeException` в критических путях

✅ **Формальные основания** — GF-грамматика, сопряжённость с доказанными тождествами, Agda-свидетельства

✅ **Наблюдаемость** — полная трассировка воспроизведения, поля восстановления документируют причину/стратегию/доказательство

### 4.2 Слабые стороны

❌ **Неограниченный рост состояния (P0)**

Три списка растут без ограничений:
1. `gsQuarantine` — карантин предложений защиты
2. `ssProvisionalAtoms` — временные атомы (TTL есть, но нет жёсткого ограничения)
3. `ktQuarantine` — карантин плодов знаний

**Воздействие:** Риск OOM, деградация сериализации, замедление сканирования в долгоживущих сессиях.

❌ **Небезопасная обработка исключений (P1)**

1. `SomeException` в PGF ловит ВСЕ исключения, уничтожая трассировки
2. `unsafePerformIO` без `NOINLINE` может привести к гонкам данных

❌ **Векторы инъекции (P1)**

Инъекция фактов Datalog — `escapeSymbol` не экранирует `(`, `)`, `.`, `%`, синтаксически значимые в Souffle.

❌ **Граничные условия (P2)**

1. Граница безопасности песочницы использует `<` вместо `<=`
2. Молчаливые значения по умолчанию JSON маскируют повреждение состояния

❌ **Несогласованность восстановления (P2)**

`recoverRuntimeTurnState` может применять устаревшие снимки после частичного отказа записи.

### 4.3 Точки сложности

⚠️ **Множественные пути линеаризации** — GF → Haskell → JSON фоллбэк добавляет сложность

⚠️ **Двухрежимная координация** — сопряжённость элегантна, но требует тщательной координации

⚠️ **Управление состоянием** — `SystemState` с 30+ полями трудно рассуждать о целом

⚠️ **Интеграция Bridge** — SQLite, Datalog, Agda — три различных внешних системы

## 5. Возможности улучшения

### 5.1 Приоритет 1: Ограниченное вращение состояния (P0, Усилие: Низкое)

**Проблема:** Три списка состояния растут неограниченно.

**Решение:**
- `gsQuarantine`: макс. 500 записей, LRU-вытеснение
- `ssProvisionalAtoms`: жёсткое ограничение 1000 атомов
- `ktQuarantine`: макс. 200 плодов

**Обоснование:** Критический риск OOM, простая реализация, высокое воздействие.

**Файлы:** `Learning.Guardrails`, `Types.State.System`, `Core.TurnPipeline.Finalize.State`, `Learning.KnowledgeTree`

### 5.2 Приоритет 2: Типизированная обработка исключений (P1, Усилие: Низкое)

**Проблема:** `SomeException` маскирует первопричины и глотает асинхронные исключения.

**Решение:**
- Заменить на типизированный `IOException` catch
- Добавить структурированные варианты PGF-ошибок
- Добавить прагму `NOINLINE` к `gfMapLoadResult`

**Обоснование:** Улучшает отладку, предотвращает несогласованное состояние, сохраняет трассировки.

**Файлы:** `Runtime.PGF`, `Lexicon.GfMap`, `ExceptionPolicy`

### 5.3 Приоритет 3: Усиленное экранирование Datalog (P1, Усилие: Среднее)

**Проблема:** `escapeSymbol` не экранирует `(`, `)`, `.`, `%`.

**Решение:**
- Расширить экранирование для всех специальных символов Datalog
- Добавить комплексное экранирование CSV/TSV
- Тесты свойств для инъекционных векторов

**Обоснование:** Предотвращает инъекцию правил, защищает от ошибок парсера.

**Файлы:** `Bridge.Datalog.Support`, новый `Test.Suite.DatalogSafety`

### 5.4 Приоритет 4: Строгая валидация JSON (P2, Усилие: Среднее)

**Проблема:** Тяжёлое использование `.:?` с `.!=` маскирует повреждение состояния.

**Решение:**
- Строгая валидация обязательных полей
- Явные сообщения об ошибках
- Версионированные проверки миграции
