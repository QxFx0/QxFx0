## 1. Context

Phase 9 completed the autonomous exploratory learning path: the system can initiate external queries when a learning need is active but below the request threshold, with telemetry distinguishing request-driven from exploratory outcomes.

However, there was still no systematic way to:
1. Extract and audit historical learning traces from a session.
2. Generate bounded, versioned calibration candidates from those traces.
3. Evaluate candidates offline before any live state mutation.
4. Promote only non-regressing candidates with rollback-ready versioning.

Phase 10 introduces the **offline training cycle**: a pure, deterministic pipeline that turns system-state history into actionable calibration decisions without touching live-turn state.

## 2. Decision

### 2.1 Pure offline execution

The training cycle is a pure function:

```haskell
runTrainingCycle :: SystemState -> TrainingCycleConfig -> UTCTime -> TrainingCycleOutcome
```

It takes a snapshot of `SystemState` (which already carries `ssCalibrationSnapshots`, `ssKnowledgeTree`, `ssLearningNeedState`) and returns a fully auditable `TrainingCycleOutcome`. No live state is mutated.

### 2.2 Dataset extraction from existing telemetry

Instead of adding new logging infrastructure, the cycle reuses `CalibrationSnapshot` records already persisted in `SystemState`:

- `SignalComponents` (conatus trend, uncertainty trend, loop risk, branch health)
- `CalibrationDecision` (ApplySignal, HoldLowConfidence, HoldGuardrails, HoldNoNeed)
- Learning need levels and knowledge-tree health proxies

The extracted `TrainingDataset` is split 70/30 into train/eval subsets and carries `DatasetStats` (total turns, accepted/rejected proposals, transport errors, fallback-heavy sessions).

### 2.3 Bounded candidate generation

Candidates are generated by applying the **existing** bounded adaptation functions `adaptSalienceWeights` and `adaptFieldHeuristics` to a fixed grid of perturbation signals:

```haskell
defaultTrainingSignals = [-0.30, -0.20, -0.10, 0.10, 0.20, 0.30]
```

Each signal produces one `SalienceWeights` candidate and one `FieldHeuristics` candidate. Total pool: 12 candidates, well inside the 10–30 bound.

Every candidate carries:
- `CalibrationId` for versioning
- `CandidateType` (Salience or Field)
- Source run ID and generation timestamp for provenance

### 2.4 Proxy offline evaluation (fail-closed)

Because we do not replay full N-turn pipelines for each candidate (that would exceed the low-RAM envelope), evaluation uses **proxy metrics** derived from the historical `TrainingTrace` window:

| Metric | Proxy | Good direction |
|--------|-------|----------------|
| Conatus trend delta | Slope of need levels before/after candidate adjustment | Negative (trend flattening) |
| Uncertainty delta | Oscillation amplitude before/after | Negative (less volatile) |
| Repair-loop frequency delta | Fraction of traces with repair-loop count > 0 | Negative |
| Reject-rate delta | Fraction of non-`CdApplySignal` decisions | Negative |
| Net score | Weighted composite (0.35/0.25/0.25/0.15) | Positive |

The adjustment is a conservatism factor computed from the candidate's parameter deltas:
- Higher `weightFieldConfidence` / lower `weightCounterfactual` → more conservative
- Lower `fhHolisticStreakBoostRate` → more conservative

Conservative candidates damp high need levels (> 0.5) and slightly boost low ones, simulating the stabilizing effect they would have on live routing.

### 2.5 Strict acceptance policy (non-regression)

A candidate is accepted only if **all** of the following hold:

1. Eval subset contains ≥ 3 traces (insufficient signal → reject).
2. `emConatusTrendDelta` ≤ 0.05 (no significant regression).
3. `emUncertaintyDelta` ≤ 0.05 (no increased oscillation).
4. `emRepairLoopFreqDelta` ≤ 0.05 (no increased repair loops).
5. `emRejectRateDelta` ≤ 0.05 (no increased reject rate).
6. `abs emNetScore` ≥ 0.001 (candidate is not a no-op).

Any failure produces a typed `TrainingRejectReason`:
- `TrRegressionConatus`
- `TrRegressionUncertainty`
- `TrRegressionRepair`
- `TrRegressionRejectRate`
- `TrUnstableVariance`
- `TrInsufficientSignal`

### 2.6 Promotion with rollback linkage

The best accepted candidate is promoted via `promoteCandidate`, which wraps it in a `CalibrationEntry` with:
- `ceStatus = Accepted`
- `cePrevId` pointing to the previous stable version
- `ceDecidedTurn = currentTurn`

Rollback is supported via `rollbackTrainingCycle`: it marks the entry `RolledBack`, updates the decided turn, and returns the previous `CalibrationId` to restore.

### 2.7 Telemetry completeness

`TrainingCycleOutcome` carries:
- `tcoCycleId` — human-readable cycle identifier
- `tcoDatasetStats` — extracted dataset statistics
- `tcoCandidates` — full evaluation table (sorted by net score, best first)
- `tcoPromotedCandidate` — the single winner, or `Nothing` if all rejected
- `tcoPreviousVersion` — the version that was current before promotion
- `tcoRollbackEntry` — populated only if a rollback was simulated (test-only)

## 3. Consequences

- **No live-turn mutations**: the cycle is purely observational until a promoted candidate is explicitly applied by a future caller.
- **Bounded compute**: 12 candidates × proxy evaluation over a small window is O(1) and low-RAM safe.
- **Honest proxy**: the evaluation is explicitly documented as a proxy, not a full turn replay. It is deterministic and reproducible.
- **Rollback-ready**: every promotion links to the previous version, enabling automatic reversion if degradation is detected later.
- **Telemetry-integrated**: the cycle reuses existing `CalibrationSnapshot` records, avoiding new logging infrastructure.

## 4. Acceptance Criteria

- [x] `TrainingDataset` extraction from `SystemState` with 70/30 split and `DatasetStats`.
- [x] `generateCandidates` produces 12 bounded, versioned, provenanced candidates.
- [x] `evaluateCandidate` computes proxy deltas and enforces strict non-regression policy.
- [x] `promoteCandidate` creates an `Accepted` `CalibrationEntry` with `prevId` linkage.
- [x] `rollbackTrainingCycle` reverts to the previous `CalibrationId`.
- [x] `runTrainingCycle` is pure and returns a fully populated `TrainingCycleOutcome`.
- [x] Fast suite: 574/574 PASS; full suite: 701/701 PASS.
- [x] Architecture gate: PASS; GF quality gate: PASS.

## 5. Residual Risks

- **Proxy fidelity**: the lightweight proxy evaluation does not replay full turns. A candidate that scores well on proxy metrics might still regress under real routing. Future work: full N-turn replay on a high-RAM runner.
- **Signal grid coarseness**: `defaultTrainingSignals` uses only 6 values. Finer-grained search or gradient-based optimisation may be needed as the parameter space grows.
- **Field heuristic adaptation**: `adaptFieldHeuristics` adapts `Double` fields only; `Int` fields (window size) are fixed. Future work may require integer-grid search.
- **No cross-validation**: the 70/30 split is positional, not randomised. With small trace counts (< 20) this can produce biased splits. Minimum threshold mitigates but does not eliminate the risk.
