# 10 Концепций развития системы QxFx0

> Контекст: QxFx0 — Haskell-система философского диалога, 403 модуля, ~70k LOC. Текущее состояние: Representation–Execution Gap (механизмы безопасности есть, но не подключены к production), 3 подтверждённых бага (декоративный гейт, NixGuard fail-open, нет -Werror), SystemState god-record (44 поля), ~15K LOC мёртвого кода. Phase 1 (CI gates) завершена, Phase 2 не начата.

---

## Концепция 1: Дисциплина раньше скорости (Incremental Hardening)

**Философия:** Система не может расти, пока её фундамент не выполняет то, что обещает. Каждый механизм безопасности должен **выполняться** в production, а не просто **присутствовать** в коде.

**Принципы:**
- Строгая последовательность этапов — ни один шаг не начинается без завершения предыдущего
- Критерий каждого изменения: не только «компилируется ли», но и «сохраняется ли информация через границы»
- Никакого нового функционала до закрытия критических точек

**Шаги:**
1. Wire `composeDefinitionWithGates` в production (или проверка `gvOverall` в `composeDefinition`)
2. NixGuard: fail-closed по умолчанию, `Blocked` вместо fallback
3. `-Werror` для redundant patterns — 207 мёртвых веток становятся ошибками
4. Content quality gate — тесты проверяют «воду», а не только «трубы»
5. Разбить SystemState на layer-specific records
6. Release artifact — known-good baseline binary

**Риски:**
- Долгое отсутствие видимого прогресса для стейкхолдеров
- При включении -Werror обнаружится, что мёртвые ветки маскируют логические ошибки
- Сопротивление команды: «работает же»

**Когда выбирать:** Система используется или приближается к использованию в реальных сценариях. Долг растёт быстрее погашения.

## Концепция 2: Хирургическая декомпозиция (Surgical Extraction)

**Философия:** Монолит с god-record и циркулярными зависимостями нельзя исправить патчами. Нужно вырезать слои в независимые пакеты с контролируемыми экспортами, создавая принудительные границы.

**Принципы:**
- Каждый слой = cabal-пакет с `exposed-modules` / `other-modules` границами
- SystemState разбивается на `TypesState`, `CoreState`, `SemanticState`, `SelfState`, `RenderState` — каждый слой видит только своё
- Циркулярные зависимости становятся ошибками компиляции, а не предупреждениями

**Шаги:**
1. Инвентаризация: какие модули импортируют какие (cabal `mixins` или `import: hiding`)
2. Выделить Types в отдельный пакет — чистые типы, без логики
3. Выделить Core — без зависимости на Semantic/Self/Render
4. SystemState → `RuntimeContext` (Core) + `DialogueState` (Semantic) + `SelfModel` (Self) + `RenderConfig` (Render)
5. Каждый пакет имеет свой test-suite
6. Bridge становится adapter-слоем между пакетами

**Риски:**
- Большой рефакторинг без видимого функционального прогресса
- Может вскрыть скрытые зависимости, которые маскируются god-record'ом
- Временная деградация производительности при межпакетных вызовах

**Когда выбирать:** Циркулярные зависимости блокируют разработку. Добавление любого поля в SystemState ломает несколько слоёв.

## Концепция 3: Контент вместо труб (Test-Driven Quality)

**Философия:** 1161 тест-кейс проходит, но ни один не проверяет, имеет ли ответ смысл. Тесты проверяют «трубы» (routing, типы, round-trip encoding), но не «воду» (семантическое содержание, поведенческую корректность). Система может генерировать бессмысленный/не по теме ответ — и все тесты зелёные.

**Принципы:**
- Тест должен проверять **поведенческий результат**, а не структурную корректность
- «Ответ на 'что такое свобода' должен быть о свободе» — это базовый тест, которого нет
- Content quality gate = обязательный этап в CI, не опциональный

**Шаги:**
1. Определить 50 философских вопросов-эталонов (свобода, справедливость, сознание, бытие...)
2. Для каждого — критерии: релевантность темы, связность аргументации, отсутствие противоречий с предыдущими репликами
3. Реализовать content quality gate: LLM-судья или эвристический валидатор
4. Добавить в CI: если content quality падает — red build
5. Регрессионный набор: каждый раз те же 50 вопросов, метрики не должны ухудшаться
6. Расширить до 200+ вопросов по мере развития

**Риски:**
- LLM-судья может быть необъективным или дорогим
- Эвристический валидатор может быть слишком грубым
- Фиксация эталонов может ограничить креативность системы

**Когда выбирать:** Система генерирует текст, но качество непредсказуемо. Нужно обеспечить минимальный уровень осмысленности.

## Концепция 4: Нулевой долг (Aggressive Cleanup)

**Философия:** ~15K LOC мёртвого и дублированного кода (~17% кодовой базы) — это балласт, который замедляет каждое изменение. Удалить всё мёртвое, устранить дубликаты, потом строить на чистом фундаменте.

**Принципы:**
- Мёртвый код — это не «может пригодиться», это «мешает сейчас»
- Дублирование Proposition*Admission типов (23 типа, 799 LOC) — выбрать один набор, удалить другой
- 23 мёртвых Python-скрипта (13,495 LOC) — удалить без сожаления
- 19 ADR в proposed/ без accepted/ — либо принять, либо отклонить

**Шаги:**
1. Удалить 4 truly dead Haskell модуля (199 LOC)
2. Удалить 5 dead Thresholds sub-modules (574 LOC)
3. Объединить 23 Proposition*Admission типа (799 LOC → один canonical набор)
4. Удалить 23 мёртвых Python-скрипта (13,495 LOC)
5. Решить судьбу 19 proposed ADR — принять или отклонить
6. Очистить 45+ old gate result reports
7. Включить -Werror — мёртвые ветки становятся ошибками
8. Результат: ~15K LOC меньше, чистая кодовая база

**Риски:**
- Удаление «мёртвого» кода может вскрыть скрытые зависимости
- Команда может сопротивляться удалению «потенциально полезного» кода
- Дубликаты могут иметь тонкие различия, которые важны

**Когда выбирать:** Кодовая база настолько велика, что навигация стала невозможной. Каждое изменение требует проверки через массу мёртвого кода.

## Концепция 5: Event-Sourcing архитектура

**Философия:** В Types/State/Governance.hs уже есть полная event-sourcing система (1117 LOC, 40+ типов событий). Вместо god-record SystemState, сделать всю систему event-sourced: состояние = свёртка событий, каждое изменение = событие в журнале.

**Принципы:**
- Состояние системы = `foldEvent :: Event -> State -> State`
- Каждое действие генерирует событие, которое записывается в журнал
- SystemState заменяется на `EventLog` + `projectedState`
- Воспроизведение журнала = восстановление любого состояния в любой момент времени
- Governance = фильтр событий, а не отдельный механизм

**Шаги:**
1. Инвентаризация существующих 40+ типов событий в Governance.hs
2. Определить `Event` как объединение всех типов событий
3. Реализовать `foldEvent` для каждого слоя
4. SystemState → `projectedState :: EventLog -> LayerState`
5. TurnPipeline генерирует события вместо мутации состояния
6. Governance = `validateEvent :: Event -> GateVerdict`
7. Воспроизведение журнала = тестирование (given events → expected state)

**Риски:**
- Большой архитектурный сдвиг, может дестабилизировать систему
- Производительность: свёртка журнала при каждом запросе
- Существующая event-sourcing система может быть неполной

**Когда выбирать:** Нужно воспроизводимость, аудит, откат состояний. Governance должна быть неотделима от основного потока.

## Концепция 6: Адверсариальное упрочнение (Red Team Approach)

**Философия:** Вместо постепенного исправления — активно пытаться сломать систему. Найти каждый fail-open путь, каждый декоративный гейт, каждую границу, уничтожающую информацию. Исправлять по принципу «самый опасный сначала».

**Принципы:**
- Red team: один разработчик ищет уязвимости, другой — исправляет
- Каждая уязвимость = эксплойт (конкретная последовательность действий, которая обходит защиту)
- Приоритет по потенциальному ущербу, а не по лёгкости исправления
- Fail-open = уязвимость по умолчанию

**Шаги:**
1. Red team аудит: найти все fail-open пути (NixGuard, composeDefinition, unsafePerformIO ×7)
2. Для каждого — написать эксплойт (тест, демонстрирующий обход)
3. Исправить: fail-closed везде, где нарушение может привести к некорректному выводу
4. Red team аудит: найти все границы, уничтожающие информацию (T.pack . show ×40, 14 silent swallow sites)
5. Для каждого — продемонстрировать потерю данных
6. Исправить: structured error channel, provenance preservation
7. Red team аудит: найти все декоративные механизмы (тесты проходят, но поведение не проверяется)
8. Исправить: content quality gate

**Риски:**
- Может быть деморализующим: каждый аудит находит новые проблемы
- Фокус на безопасности может отвлечь от функционального развития
- Эксплойты могут требовать сложной инфраструктуры для демонстрации

**Когда выбирать:** Система обрабатывает критические данные или используется в сценариях, где некорректный вывод хуже, чем отсутствие вывода.

## Концепция 7: Минимальный жизнеспособный релиз (Cut and Ship)

**Философия:** Ни одного релиза не было. Система развивается 70k+ LOC без обратной связи от реального использования. Лучше вырезать то, что работает, выпустить, получить обратную связь — потом решать, что развивать.

**Принципы:**
- Release = known-good baseline, не идеальная система
- Вырезать всё, что не работает (GameTheory не подключён — удалить из интерфейса)
- Bayesian capped 0.08 — оставить как есть, пометить как experimental
- LLM circuit breaker — минимальная защита от runaway generation
- Интеграция 5% → достаточно для базового сценария

**Шаги:**
1. Определить минимальный сценарий: пользователь задаёт философский вопрос → система генерирует осмысленный ответ
2. Вырезать всё, что не входит в этот сценарий (Learning pipeline, GameTheory, Dream, Orbital — за флагами)
3. Wire базовый путь: Prepare → Plan → Route → Render → Finalize с gate enforcement
4. LLM circuit breaker: если генерация занимает >N секунд или >M токенов — abort
5. Smoke test: 10 философских вопросов, ответы проверяются вручную
6. Tag v0.1.0 — baseline binary
7. Собрать обратную связь, определить приоритеты для v0.2.0

**Риски:**
- Релиз с известными дефектами может повредить репутации
- Вырезание функционала может удалить то, что на самом деле важно
- Ручная проверка 10 вопросов не масштабируется

**Когда выбирать:** Система никогда не использовалась в реальных сценариях. Долг растёт, а ценность не подтверждена.

## Концепция 8: Формальная верификация (Agda/Category Theory Path)

**Философия:** QxFx0 уже построен на категориальных и феноменологических идеях: адъюнкция Holistic⊣Formal, 5-компонентное поле, FMAR, R5Dynamics. Вместо тестирования — формально доказать корректность критических путей используя Agda (уже в стеке сборки).

**Принципы:**
- Тесты проверяют конкретные случаи, доказательства — все случаи
- Критические пути (TurnPipeline, gate enforcement, error propagation) формализуются в Agda
- Категориальная структура (адъюнкция, Conatus) — не метафора, а спецификация
- Доказательство = обязательный артефакт, не опциональный

**Шаги:**
1. Формализовать TurnPipeline как композицию морфизмов в Agda
2. Доказать: если все gates возвращают Approved, то результат = GeneratedSurface с непустым содержанием
3. Формализовать gate enforcement: `composeDefinition` вызывает `validatePath`
4. Доказать: NixGuard fail-closed → нет пути, где governance bypassed
5. Формализовать error propagation: ошибка на любом этапе сохраняет provenance
6. Extract Haskell код из Agda доказательств (или использовать как спецификацию)
7. CI: Agda proof checking как gate

**Риски:**
- Очень высокая стоимость входа: формальная верификация медленна
- Может оказаться, что категориальная структура не соответствует реализации
- Доказательства могут быть слишком абстрактными для практической пользы

**Когда выбирать:** Критические пути требуют гарантий, а не вероятностей. Команда имеет опыт формальных методов.

## Концепция 9: Генеративный рост (Feature-First Expansion)

**Философия:** Долг — это цена роста. Система уже добавила 2526 LOC нового pipeline. Вместо остановки — продолжать генеративную разработку, но с дисциплиной: каждый новый модуль должен быть self-contained, с собственными тестами и gates.

**Принципы:**
- Новый код = чистый, self-contained, с gates и тестами
- Старый долг = отдельный трек, не блокирующий новый функционал
- Каждый новый модуль объявляет свои зависимости явно (no implicit SystemState access)
- «Долг растёт медленнее, чем ценность» — балансирующий критерий

**Шаги:**
1. Определить новые возможности: multi-turn dialogue memory, cross-topic reasoning, user modeling
2. Каждый новый модуль: cabal-пакет или isolated namespace, собственные gates, собственные тесты
3. Новый код не зависит от SystemState напрямую — только через интерфейс
4. Старый долг: 1 день в неделю на погашение (composeDefinition fix, NixGuard, -Werror)
5. Метрика: ratio нового кода к погашенному долгу — не должна превышать 3:1
6. Когда ratio падает до 1:1 — можно ускорить генерацию

**Риски:**
- Долг может расти быстрее, чем ожидается
- Новый код может повторять паттерны старого (god-record, fail-open)
- Без структурной дисциплины новый код создаёт новый долг

**Когда выбирать:** Система доказала базовую ценность, но нуждается в возможностях. Команда может поддерживать два трека параллельно.

## Концепция 10: Мульти-режимная архитектура (Hybrid Governance)

**Философия:** Вместо одного режима governance для всех сценариев — поддерживать несколько явно. Пользователь или контекст выбирает режим: strict (fail-closed, все gates enforced), permissive (fail-open, best-effort), experimental (no gates, raw generation). Режим — это не env-var, а first-class концепция в типах.

**Принципы:**
- `data GovernanceMode = Strict | Permissive | Experimental`
- Каждый режим определяет: какие gates enforced, какой fail behavior, какое логирование
- Режим передаётся через типы, не через env-vars
- Production default = Strict. Permissive = только для разработки. Experimental = sandboxed.
- Режим не может быть изменён во время диалога (immutability)

**Шаги:**
1. Определить `GovernanceMode` как алгебраический тип
2. Каждый gate: `validatePath :: GovernanceMode -> Path -> GateVerdict`
3. Strict: все gates enforced, fail-closed, full provenance logging
4. Permissive: gates evaluated but не blocking, warnings logged
5. Experimental: gates bypassed, raw output, sandboxed environment
6. SystemState получает `ssGovernanceMode :: GovernanceMode` (immutable after init)
7. CLI флаг: `--governance=strict|permissive|experimental`
8. Тесты: каждый режим имеет свой test-suite

**Риски:**
- Может легитимизировать fail-open как «permissive режим» вместо бага
- Усложняет тестирование: 3× комбинаций
- Пользователь может выбрать Experimental в production

**Когда выбирать:** Разные сценарии использования требуют разного уровня строгости. Исследование требует свободы, production — гарантий.

## Рекомендация

**Концепции 1, 3, 4 — комплементарны и могут выполняться параллельно:**
- Концепция 1 (wire gates) — критическая инфраструктура
- Концепция 3 (content quality) — критическая ценность
- Концепция 4 (cleanup) — критическая навигация

**Концепции 2, 5, 8 — альтернативные архитектуры**, выбираются одна.

**Концепции 7, 9 — стратегические решения** о том, что важнее: релиз или рост.

**Концепция 10 — ортогональна**, может сочетаться с любой другой.

**Оптимальная комбинация для текущего состояния QxFx0:** 1 (дисциплина) + 3 (контент) + 4 (cleanup) → 7 (релиз) → 2 (декомпозиция) → 5 или 8 (архитектура следующего поколения).
